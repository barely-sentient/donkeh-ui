WebView reference

A webview embeds a real browser document in your UI. On desktop, Chromium Embedded Framework (CEF) renders the page offscreen; Donkeh uploads each painted frame as a texture and draws it through the same display list as every other element. The webview therefore behaves like a replaced element — it takes part in layout, stacking order, clipping, opacity and transforms — instead of being a separate native window floating above the app.

What a webview actually is

Unlike iframe, object and embed, which are currently just styled placeholder boxes, webview creates a live Chromium browser. HTML, CSS and JavaScript inside it are parsed and executed by Chromium, not by Donkeh. Donkeh only owns the element’s box and decides where the browser’s pixels appear on screen.

The browser does not draw into the Donkeh window directly. CEF paints into an offscreen buffer; Donkeh converts those pixels to RGBA, copies them into a texture held by the image cache, and emits a normal image draw at the element’s paint position. This is the same pipeline used by video frames, which is why the webview can sit behind or in front of other content and be clipped or transformed by its ancestors.

Behaviour by concern

ConcernHow Donkeh handles it
LayoutReplaced content with a default 300 × 150 box, the width/height attributes, or CSS. The box is the browser viewport; resizing it resizes the CEF view.
PaintingEach CEF frame becomes a texture in the shared image cache and is drawn as an ImageSpec. It obeys z-index, stacking contexts, scroll offsets, clip, opacity and transforms.
InputPointer move/press/release, wheel and key events are forwarded into the browser by the host. The webview takes focus on press; focusing another control gives it back.
ThreadingCEF paints on its own UI thread. Frames are copied into a per-element buffer there and uploaded to the GPU on Donkeh’s render thread, where the OpenGL context is current.
LifecycleOne browser per element, created on the first frame where the element has a src. Browsers are disposed when their element leaves the tree; CEF is shut down when the window closes.
PlatformDesktop only. Android has no WebView-to-GLES texture bridge, and the browser host mirrors the tree to real DOM, where a native iframe is the right tool.

Adding a webview

using Donkeh.UILab;
using Donkeh.Windowing;
using static Donkeh.UILab._;

<webview
    src="https://example.com"
    className="browser"
    onReady={view => view.ExecuteJavaScript(
        "document.body.style.background = '#f7f7f7'")} />
using Donkeh.UILab;
using Donkeh.Windowing;
using static Donkeh.UILab._;

H("webview", new WebViewProps
{
    Src = "https://example.com",
    ClassName = "browser",
    OnReady = view => view.ExecuteJavaScript(
        "document.body.style.background = '#f7f7f7'")
});

WebViewProps adds OnReady to the ordinary element props; Src, ClassName, styles and event handlers are the standard ones. Plain Props also works if you do not need the ready callback: H("webview", new Props { Src = "..." }).

A stylesheet can size and place it like any other box: 

.browser {
    width: 640px;
    height: 480px;
    border-radius: 12px;
    overflow: hidden;
}

The src attribute

Src accepts three forms:

  • An absolute URL such as https://example.com.
  • A data: URI for self-contained HTML.
  • A local path, which is resolved to a file: URI so bundled or downloaded pages can be loaded.

An element without a usable src is skipped. Changing src disposes the existing browser and creates a new one, so the page follows the prop. 

<webview src="data:text/html,<h1>Hello</h1><p>From a data URI.</p>" />
H("webview", new WebViewProps
{
    Src = "data:text/html,<h1>Hello</h1><p>From a data URI.</p>"
});

Sizing and layout

The default box is 300 × 150 CSS pixels, matching iframe. Use the width and height attributes or CSS to change it. The element’s border box becomes the browser viewport in device pixels; Donkeh resizes the CEF view whenever layout changes, including when a scroll container moves the element on screen.

Scrolling inside the loaded page is handled by Chromium. Wheel events over the element are forwarded to the browser instead of scrolling Donkeh ancestors, so the page scrolls naturally. Content outside the element is clipped by normal CSS overflow rules. object-fit is not used: the frame always fills the box.

The WebView controller

OnReady receives a WebView object. It is a thin, engine-independent control surface, so application code never has to reference CefSharp directly.

MemberDescription
AddressThe URL the browser is currently displaying.
IsLoadingWhether a document is still loading.
IsReadyWhether the underlying browser has finished being created.
Load(string url)Navigates to a URL, data URI or local path.
Reload()Reloads the current address.
ExecuteJavaScript(string script)Runs a string of script in the main frame. Fire-and-forget.
EvaluateJavaScriptAsync(string script)Evaluates script and returns the result as a string.
Back(), Forward(), CanGoBack, CanGoForwardNavigation history of the active tab.
OpenTab(url?, activate?), TabsConvenience access to the tab manager.
PluginsThe plugin context for the active tab (scripts, bindings, IPC).
 
<webview
    src="https://example.com"
    onReady={view =>
    {
        view.ExecuteJavaScript("window.__appToken = 'abc123'");
    }} />
H("webview", new WebViewProps
{
    Src = "https://example.com",
    OnReady = view =>
    {
        view.ExecuteJavaScript("window.__appToken = 'abc123'");
    }
});

The callback is invoked once, on the first frame after the browser exists. Browser creation is asynchronous, so doing work before OnReady may silently do nothing.

Events

Ordinary element event props (OnClick, OnPointerDown, OnKeyDown, and so on) can be attached to a webview like any other element. CEF navigation events are not bridged into Donkeh events yet; for simple loading state, poll IsLoading through the controller. Input events that land inside the element are forwarded to the browser, so they normally reach the page rather than Donkeh handlers.

Startup pages and configuration

Global settings live in WebViewOptions.Current. Subscribe to the static WebViewOptions.Configuring event to set them up just before CEF is initialized, or replace the instance through WebViewOptions.Use(...) with your own subclass. The class is not sealed and its members are virtual, so resolution can be overridden completely. 

WebViewOptions.Configuring += options =>
{
    options.ProtocolKey = "my-app";
    options.LoadingPage = "data:text/html,<h1>Loading…</h1>";
    options.NewTabPage = "my-app://newtab";
    options.OnWebViewReady = view => Console.WriteLine(view.Address);
};
WebViewOptions.Configuring += options =>
{
    options.ProtocolKey = "my-app";
    options.LoadingPage = "data:text/html,<h1>Loading…</h1>";
    options.NewTabPage = "my-app://newtab";
    options.OnWebViewReady = view => Console.WriteLine(view.Address);
};

LoadingPage defaults to about:blank and is shown until the document from src is ready. A single element can override it with the loading-page attribute. OnWebViewReady is a global hook invoked for every webview alongside the element-level OnReady prop.

OptionDescription
ProtocolKeyScheme registered with CEF for custom application URLs, e.g. my-app.
LoadingPagePage shown while the target document loads. Defaults to about:blank.
NewTabPagePage used by view.Tabs.Open() when no URL is given.
HomePageConvenience value for app-owned navigation.
OnWebViewReady, OnTabOpened, OnTabClosedGlobal hooks for controllers and tab lifecycle.
AssetResolver, UrlResolverCustom resolver delegates consulted before the built-in probing.

Custom URLs

Set ProtocolKey before the first browser is created and map URLs to content with AddCustomUrl. The second argument can be an embedded resource name, a file path relative to the application directory, a WebViewResource, or a per-request resolver. Automatic resolution tries embedded manifest resources first, then files, and finally the UrlResolver delegate. 

options.ProtocolKey = "my-app";

// Embedded resource or file, auto-detected:
options.AddCustomUrl("my-app://path/to/item", "path/to/embedded/asset.html");

// Literal content:
options.AddCustomUrl("my-app://newtab", WebViewResource.FromHtml("<h1>New tab</h1>"));

// Dynamic content:
options.AddCustomUrl("my-app://item/{id}", uri =>
    WebViewResource.FromHtml("<h1>" + uri.AbsolutePath + "</h1>"));

// Catch-all for the protocol:
options.UrlResolver = uri => uri.Scheme == "my-app"
    ? WebViewResource.FromFile("fallback.html")
    : null;
options.ProtocolKey = "my-app";

options.AddCustomUrl("my-app://path/to/item", "path/to/embedded/asset.html");
options.AddCustomUrl("my-app://newtab", WebViewResource.FromHtml("<h1>New tab</h1>"));
options.AddCustomUrl("my-app://item/{id}", uri =>
    WebViewResource.FromHtml("<h1>" + uri.AbsolutePath + "</h1>"));
options.UrlResolver = uri => uri.Scheme == "my-app"
    ? WebViewResource.FromFile("fallback.html")
    : null;

Additional protocols can be registered with AddProtocol(scheme, resolver). Unhandled custom URLs return a 404 page.

Tabs and history

Each webview owns a tab collection. Only the active tab is painted, but every tab keeps its own browser, history and load state. WebView delegates its navigation members to the active tab.

MemberDescription
view.TabsThe WebViewTabManager for this element.
Open(url?, activate?), Close(tab), Activate(tab)Tab lifecycle.
Next(), Previous()Cyclic tab activation.
Tabs, ActiveOpen tabs in creation order and the visible tab.
TabOpened, TabClosed, ActiveChangedEvents for binding a tab strip.
WebViewTabId, Address, Title, IsLoading, CanGoBack, CanGoForward, StateChanged, Load, Reload, Back, Forward, Activate, Close.
 
<webview
    src="my-app://item"
    onReady={view =>
    {
        var tab = view.Tabs.Open();          // uses NewTabPage
        tab.Load("https://example.com");
    }} />
H("webview", new WebViewProps
{
    Src = "my-app://item",
    OnReady = view =>
    {
        var tab = view.Tabs?.Open();
        tab?.Load("https://example.com");
    }
});

Changing an element’s src still replaces its browser and therefore its tab collection. Tabs are owned by the element, not shared between webviews.

Plugins and script injection

Plugins are the Electron-like extension point. A plugin contributes preload scripts, registers .NET objects for JavaScript, and handles IPC messages. Register plugins globally in WebViewOptions.Configuring, or use view.Plugins / tab.Plugins to add and remove them for a single view at runtime. 

WebViewOptions.Configuring += options =>
{
    options.AddPlugin(new MyPlugin());
    options.RegisterObject("files", new FileApi());
    options.OnMessage("save", msg =>
    {
        var data = msg.Read<SaveRequest>();
        msg.Reply(new { ok = true });
    });
};

public sealed class MyPlugin : WebViewPlugin
{
    public override string Name => "my-plugin";

    public override IReadOnlyList<WebViewScript> Scripts =>
    [
        WebViewScript.Preload("my.preload", @"
            window.donkeh.on('refresh', function (payload) { location.reload(); });
        ")
    ];

    public override void OnAttached(WebViewPluginContext context)
    {
        context.RegisterObject("api", new MyApi());
        context.OnMessage("open", msg => Console.WriteLine(msg.Payload));
    }

    public override void OnLoad(WebViewPluginContext context, Uri url)
    {
        context.Emit("ready", new { url = url.AbsoluteUri });
    }
}
WebViewOptions.Configuring += options =>
{
    options.AddPlugin(new MyPlugin());
    options.RegisterObject("files", new FileApi());
    options.OnMessage("save", msg =>
    {
        var data = msg.Read<SaveRequest>();
        msg.Reply(new { ok = true });
    });
};

// WebViewScript, WebViewPlugin and WebViewPluginContext are the same in plain C#.
H("webview", new WebViewProps
{
    Src = "my-app://item",
    OnReady = view => view.Plugins?.AddPlugin(new ExtraPlugin())
});

Scripts run at DocumentStart (as soon as the frame's V8 context exists, before page scripts), DocumentEnd, or never (Manual). They can be filtered by URL and restricted to the main frame. By default each snippet is wrapped in an IIFE so it does not leak declarations into the page; set Isolate = false to inject raw source.

MemberDescription
WebViewScript.Preload(id, source)Inject before page scripts.
WebViewScript.AfterLoad(id, source)Inject after the frame finishes loading.
Filter, MainFrameOnly, Isolate, EnabledControl which documents receive a script and how it is wrapped.
WebViewPluginName, Enabled, Scripts, OnAttached, OnDetached, OnContextCreated, OnLoad, OnMessage.
RegisterObject(name, target, options)Bind a .NET object; methods camelCase by default and async methods return promises.
OnMessage(channel, handler), Reply(payload)Handle JS→C# messages and answer invoke calls.
Emit(channel, payload)Raise a C#→JS event received by window.donkeh.on(channel, callback).

The injected bridge exposes window.donkeh.send(channel, payload), invoke(channel, payload) (a promise resolved by message.Reply(...)), on(channel, callback) and off(channel, callback). Set EnablePluginBridge = false or BridgeGlobalName in WebViewOptions to replace or rename it. Messages are JSON; use WebViewMessage.Read<T>() to deserialize them.

Object binding uses CefSharp's legacy binding, so objects must be registered before the browser is created. Global registrations and plugin OnAttached hooks happen automatically at that point; objects added later with RegisterObject bind through an explicit CefSharp.BindObjectAsync call.

Input and focus in detail

Because the browser is offscreen, the operating system delivers input to the Donkeh window, not to Chromium. Donkeh translates and forwards it:

  • Mouse move, press and release are converted to browser-local CSS pixels and sent with the current modifier state.
  • Wheel deltas are forwarded so the page scrolls instead of an ancestor container.
  • Key down, key up and character events are forwarded while a webview has focus.
  • Pressing inside a webview focuses it and blurs any previous webview; focusing another Donkeh control returns focus.

This means keyboard shortcuts and text input go to the page while it is focused. It also means the browser’s native chrome is unavailable: there is no address bar, context menu integration or IME composition window. Your app owns navigation through the WebView controller.

Performance

This implementation uses CEF’s CPU offscreen rendering path. Each painted frame is copied from BGRA to RGBA and uploaded in full with glTexSubImage2D; dirty rectangles are not used yet. Cost therefore scales with the element’s pixel area and with how often the page repaints. Keep webviews to sensible sizes, and prefer static pages for large surfaces.

The accelerated shared-texture path exists in CEF but is intentionally not used here. Swapping it in later would change only how frames are produced — the element, layout, input and paint integration would stay the same.

Current limitations

  • Desktop hosts only; Android and the browser DOM host do not create a CEF browser.
  • Popup widgets painted by Chromium (for example native select dropdowns and context menus) are not composited into the Donkeh frame.
  • Load state, title and history flags are available on WebViewTab; full CEF request/navigation events are not bridged into Donkeh events yet.
  • IME composition ranges and drag-and-drop from the page are not wired.
  • Every frame is uploaded in full; there is no dirty-region upload.
  • The native CEF runtime must be shipped with the application output.
